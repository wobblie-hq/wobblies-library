# Design — library-quality

## Verified current architecture (2026-07-02)

- Validation entry: `scripts/validate-examples.ts` →
  `src/examples/cli.ts` `runValidateCli(cwd)`. Supporting modules:
  `catalog.ts` (loading), `schema.ts` (zod, 520 lines), `validation.ts`
  (error formatting helpers), `public-safety.ts` (leak regexes),
  `paths.ts`, `types.ts`. Tests in `src/examples/__tests__/` and
  `src/__tests__/` (vitest).
- WOBBLIE.md format: YAML frontmatter (`id`, `purpose`, `integrations`,
  `watch`, `routines`, `deny`, `schedule`, `adapt` placeholders like
  `{{adapt.slack_channel}}`) + markdown body sections (Overview/Policy/
  Limits on stubs; richer sections like Signal threshold / Low-noise
  behavior / Output format on authored ones).
- Platform constraint (from wobblie.ai): watch rules must parse as
  "when a <event> is <action>" (`parseWatchTrigger` in @repo/core);
  free-form watch rules silently never match.
- Catalog artifacts `wobblies.json` + `examples.json` generated by
  `scripts/generate-examples.ts`; CI workflows `generate-wobblies.yml`,
  `release.yml`.

## Design decisions

### D1. Lint lives in the existing validation pipeline

New module `src/examples/authoring-lint.ts` exporting
`lintWobblie(parsed: ParsedWobblie): LintFinding[]` with
`LintFinding { ruleId, severity: "error" | "warn", message, path }`.
`runValidateCli` aggregates findings; any `error` fails the run. Rules are
data-driven entries `{ ruleId, check(parsed) }` in one array so adding a
rule never touches the runner. Boilerplate detection uses an exact-match
denylist of the current stub strings (routines, policy line, limits line)
— cheap, zero false positives; the specificity heuristic (routine must
share ≥1 non-stopword token stem with `purpose`) is `warn` severity to
start, promoted to `error` after the rewrites land.

### D2. Capability manifest is a versioned data file

`src/examples/platform-capabilities.ts` exports:

```ts
export const PLATFORM_CAPABILITIES = {
  version: "2026-07-02",
  integrations: ["github", "slack", "linear", "notion", "jira", "sentry", "vercel"],
  actions: {
    write: ["comment", "create_pr", "create_issue", "update_issue", "label",
            "request_review", "slack.message", "slack.reaction", /* provider writes */],
    read:  ["github.list_prs", "github.list_workflow_runs", "slack.read_channel"], // pending platform Task 1
    sandbox: ["run_command"],
  },
  sandboxTools: ["node", "pnpm", "git", "gh", "jq", "curl"], // pending platform Task 2
} as const;
```

Entries marked `pending` carry a `pendingSince` note; the capability lint
treats pending capabilities as available but emits a `warn` so the library
doesn't block on platform sequencing. Update procedure documented in the
file header.

Capability requirement detection mirrors the platform's capability-lint
keyword map (wobblie-reliability Task 4) — keep the two rule lists
textually identical and note the duplication in both files until a shared
package exists (explicitly out of scope here).

### D3. Rewrite template

Every rewrite follows the authored-wobblie skeleton (model:
`github-activity-digest`, `docs-drift-maintainer`):

- frontmatter: specific `routines` (3–6, imperative, referencing the
  wobblie's actual signals), triggers = schedule XOR watch (both only with
  a `## Trigger rationale` body section), tailored `deny`
- body sections in order: `## Overview`, `## Scope`,
  `## Signal threshold` (include/exclude lists), `## Low-noise behavior`
  (no-op conditions), `## Output format` (exact action + content contract),
  `## Limits` (matching trigger type)
- adapt placeholders for anything repo-specific (channels, thresholds,
  paths)

Nature classification decided in the task briefs: 7 stubs are scheduled
scanners mislabeled with PR triggers (flaky-test-detector,
security-advisory-watcher, stale-pr-closer, test-coverage-gate,
type-coverage-monitor, unused-dependency-remover, release-drafter — the
last watches releases/merges, decide in-task), 13 are genuinely
PR-triggered and drop their schedule.

### D4. Fixture format

`wobblies/<id>/fixtures/trigger.json` + `expected.json`
(+ optional `noop-trigger.json`, `noop-expected.json`).

```jsonc
// expected.json
{
  "actions": [
    { "type": "comment", "targetPattern": "^[\\w.-]+/[\\w.-]+#\\d+$",
      "contentMustMatch": ["\\bbranch name\\b"], "contentMustNotMatch": ["```"] }
  ],
  "maxActions": 1,
  "allowNoop": false
}
```

Zod schema in `src/examples/fixture-schema.ts`; vitest suite
`src/examples/__tests__/fixtures.test.ts` validates every wobblie has
fixtures, they parse, and expected action types ∈ capability manifest.
The platform replay harness consumes the same files (coordinate field
names with wobblie.ai wobblie-reliability Task 6.4 — that harness's
fixture loader is the consumer contract; if it exists first, match it).

### D5. Generated-artifact freshness gate

CI step: run `generate:examples`, then `git diff --exit-code wobblies.json
examples.json` — fails when regeneration was forgotten.
